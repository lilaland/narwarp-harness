# Move Narwarp's brain out of the terminal

Don't build the harness inside the Rust fork, and don't spend a day merging Zap first. Freeze Narwarp at its `phase-4/watcher-and-polish` tip as your daily terminal and build a standalone Python daemon, `narwarpd`. It is the only writer of one SQLite store (tickets, runs, boards, calendar plan, external links). It exposes an MCP server, an `nw` CLI and a Claude Code hook sink, drives Claude Code through Anthropic's own background-session supervisor, and gives Ollama only narrow, schema-bound jobs. A Textual TUI is its first client, and a replaceable one. The fork is the wrong home: **Zap has taken no Warp changes since May 7 and has made four commits since August**, while Warp itself is merging an ACP harness runner and already ships a terminal-agnostic agent CLI ([Warp docs](https://docs.warp.dev/agents/cli/)). Staying means maintaining **1.14M lines of Rust** alone to compete with a funded team inside its own codebase. Adopting Paperclip, Multica or Gas City is also wrong. None of them has a Work/Life mode, calendar time-blocking, or a first-class way for one ticket to group many Linear issues, and those are exactly the features that make this product yours. Their schemas are still worth copying. Of the twelve systems the design needs, **only three call for a frontier model** (decomposition, coding, life planning). Three are schema-bound local-model jobs and six are plain code, because agents working without a central checker amplify errors about four times more than centrally validated ones ([Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)). Several parts of the plan will fail as written: four columns hide the review bottleneck, free-form agent collaboration makes results worse, an auto-reshuffled calendar produces the churn Reclaim backed away from, nag-based accountability stops working within weeks, and both reading a work Discord and writing a work calendar depend on admins you don't control. The first slice is one supervised loop: a typed prompt becomes an auto-filed ticket, a background Claude Code session works it in a git worktree, its status and questions land on the ticket's board through hooks, and you answer or approve from the TUI.

## Twelve systems, and only three need a frontier model

The failure evidence decides what is code and what is a model. In Google's 180-configuration study, **independent agents amplified errors 17.2× while centralized coordination held that to 4.4×**, because the orchestrator acted as a validation bottleneck. Every multi-agent variant also made sequential planning 39–70% worse ([Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)). Across 1,600 annotated traces, MAST found that failed verification and stopping too early (or not knowing when to stop) are far more common than an agent ignoring another agent. In ChatDev, adding an objective-verification step was the biggest single fix, at +15.6% ([MAST](https://arxiv.org/html/2503.13657v3)). OpenAI's Symphony makes its orchestrator "the only component that mutates scheduling state" ([Symphony SPEC](https://github.com/openai/symphony/blob/main/SPEC.md)). Narwarp should do the same. **Deterministic code owns state, scheduling and gates. Models classify, summarize, decompose, code and narrate, and code checks every model output before it changes anything.**

The guardrails rest on the strongest security evidence available. Meta's "Rule of Two" says one session may combine at most two of untrusted input, private data and the ability to act or communicate externally ([Meta AI](https://ai.meta.com/blog/practical-ai-agent-security/)). That is why the reader has no tools and coding workers never see raw email. BrokenClaw turned a single unopened email into code execution on OpenClaw after fake end tags defeated its "untrusted content" wrappers ([veganmosfet](https://veganmosfet.codeberg.page/posts/2026-02-02-openclaw_mail_rce/)). So wrappers are basic hygiene, not a security boundary. A Meta alignment lead told OpenClaw to only suggest deletions. She suspects the instruction was lost when the agent compacted its context, and it then deleted 200+ emails ([OECD](https://oecd.ai/en/incidents/2026-02-23-d55b)). **Approval rules must be config that code enforces, never prompt text.** One ICML 2026 workshop paper, not yet replicated, found that signing messages with their provenance cut injection between agents by 91% ([ICML](https://icml.cc/virtual/2026/67971)). Signing is cheap enough to adopt on that evidence alone.

Size local models to the job. Tool calling gets much less reliable between 9B and 4B, where Qwen3.5 drops from 66.1 to 50.3 on the BFCL-V4 tool-calling benchmark ([Qwen](https://huggingface.co/Qwen/Qwen3.5-9B)), while summarizing is a job small models do well: Qwen3-8B has a 4.8% hallucination rate on Vectara's summarization leaderboard ([Vectara](https://github.com/vectara/hallucination-leaderboard)). The Mac-specific trap is context length. Ollama defaults to **a 4k context when less than 24 GiB of memory is available to the GPU** and recommends at least 64k for agents ([Ollama](https://docs.ollama.com/context-length)), so a 16–32 GB MacBook will silently cut off digest input unless `OLLAMA_CONTEXT_LENGTH` is set. On 16–32 GB, keep local models to triage, digests and the reader and send all coding to Claude; a 27B local coding model is realistic only at 64 GB and up. Tusk belongs in the human-facing outputs (digests, nudges, ritual prompts), not in worker system prompts, where it would use up context on every turn.

## A local daemon with thin clients beats four alternatives

By late 2026, multi-agent harnesses had converged on three moves: separate the process that hosts agents from the UI, give each task its own git worktree, and read status from hooks or structured protocols instead of scraping terminal text. Claude Code adopted the first in May 2026 with a supervisor that keeps background sessions running after you close the terminal and through sleep ([Claude Code agent view](https://code.claude.com/docs/en/agent-view)). Superset backs its terminals with a daemon so processes and scrollback "survive app restarts and updates" ([Superset](https://docs.superset.sh/llms-full.txt)). Codex puts one harness behind a JSON-RPC app server for every surface ([Codex app-server](https://learn.chatgpt.com/docs/app-server)). Wrappers that mainly offered a UI for running agents in parallel worktrees fared worst. Terragon shut down in January ([Terragon](https://github.com/terragon-labs/terragon-oss)), Crystal was deprecated in February ([Crystal](https://github.com/stravu/crystal)), and Vibe Kanban announced its sunset on 2026-04-10 ([Vibe Kanban](https://www.vibekanban.com/blog/shutdown)).

| Shape | Closest precedents | What it gets you | Where it breaks for you |
|---|---|---|---|
| **A. Everything in the fork**: WarpUI board, calendar and message views, Diesel tables, a Rust loop for Ollama agents, panes owned by Narwarp | cmux, Superset's desktop app, Warp's own ACP runner | One app, native panes, vault and retrieval already in place | The harness only exists while the GUI runs; roughly 4–7k more lines of Rust wired through a 22,334-line central UI file; WarpUI has no calendar or date component; every change waits on a Rust rebuild |
| **B. Thin dashboard over Anthropic's supervisor**: a small TUI and store over `claude --bg`, `claude agents --json`, hooks and per-session message sockets | Claude Code agent view, Agent Deck, cmux | Least code, full Claude Code features, the clearly sanctioned subscription path | Provides nothing for boards, calendar, integrations or local models; the preview features it relies on change often |
| **C. Local daemon with thin clients** (recommended): Python `narwarpd` owns the store, sync, scheduler, MCP server, CLI and hook sink, with B built in as the Claude lane | Superset's host service, OpenCode's server, Codex app server, Multica's laptop daemon, Symphony | Survives UI restarts; agents and your phone reach it directly; Python's integration libraries; works in any terminal | You own a daemon and a schema; Textual's maintenance is thinning |
| **D. Adopt a platform**: Paperclip or Multica as the backend, with your TUI on top | Paperclip, Multica | Goals, recurring tasks, approvals, budgets and connectors on day one | No Work/Life mode or time-blocking; TypeScript or Go on Postgres; built web-first; upstream publishes a new release tag almost every day |
| **E. Hierarchy of supervising agents**: "mayor", "witness" and "deacon" agents directing workers | Gas Town, Gas City | Scales to dozens of agents | Built for setups of about 100 agents using about a billion tokens a day ([Every](https://every.to/context-window/inside-the-100-agent-software-factory)); you will run three to five |

C wins because every one of your features is mostly data, orchestration and integrations. Only C lets agents, your phone and your terminal reach that data whether or not a GUI is open. It also contains B, so the Claude lane needs almost no runtime code. And it keeps A available later as a thin client: a Narwarp side panel or slash commands that call the daemon's API. That matches Zap's own principle that "the terminal becomes one client among many" ([Zap roadmap](https://github.com/zerx-lab/zap/blob/main/docs/roadmap.md)).

### The recommended shape

```
clients      Textual TUI (board, calendar, needs-you)  ·  nw CLI  ·  "Narwarp HQ" Discord bot  ·  phone via Remote Control
                │  versioned JSON API on a unix socket
narwarpd     Python, started by a LaunchAgent; sole writer of narwarp.db (SQLite WAL + FTS5; sqlite-vec later)
  ├─ reconciler     claims, 3–5 agent cap, stall timers, lane policy, ticket → session map for respawn
  ├─ board service  typed messages, read/ack, handoffs, signed approvals
  ├─ interfaces     MCP server "narwarp" (stdio) · HTTP hook sink on 127.0.0.1 · nw CLI
  ├─ sync           Linear · GitHub · Gmail/IMAP · Discord gateway · Google Calendar (cursors + write journal)
  ├─ planner        greedy repair always on · CP-SAT for morning and weekly plans
  └─ local jobs     Ollama: triage · digests · quarantined reader · nudge wording
                │  dispatch
Claude lane  claude --bg -n NW-142 -w nw-142 --settings narwarp-hooks.json   (Anthropic's supervisor)
             state: claude agents --json + HTTP hooks · approvals: claude attach in a tmux pane
Local lane   same binary with ANTHROPIC_BASE_URL=http://localhost:11434 in its own CLAUDE_CONFIG_DIR
```

**Dispatch.** The daemon starts each ticket with `claude --bg`, a name and a worktree, and passes a Narwarp hook file through `--settings`. The hooks then fire only in harness sessions, the pattern Gas Town uses ([Gas Town hooks](https://raw.githubusercontent.com/steveyegge/gastown/main/docs/HOOKS.md)). Whether these flags combine cleanly is a Phase 0 test.

**Status.** State comes from `claude agents --json`, which Anthropic calls "the supported way to read session state from outside Claude Code". The `~/.claude/jobs` files "are not a stable interface" ([agent view](https://code.claude.com/docs/en/agent-view)). Push events come from HTTP hooks that POST to the daemon ([hooks](https://code.claude.com/docs/en/hooks)).

**Context.** Context goes in at `SessionStart` and `UserPromptSubmit` as short headers written as facts. Each injection is capped at 10,000 characters, and text phrased as commands "can trigger Claude's prompt-injection defenses" ([hooks](https://code.claude.com/docs/en/hooks)).

**Approvals and hands-on work.** You attach to the session in a tmux pane. Python has no maintained terminal widget: textual-terminal was last released in 2023 ([PyPI](https://pypi.org/project/textual-terminal/)). tmux is also the pane host Claude Code's agent teams use ([agent teams](https://code.claude.com/docs/en/agent-teams)). Agent teams themselves stay off. They are still experimental, don't spawn in `-p` or SDK sessions, and in-process teammates don't come back after `/resume`.

**Local lane.** The same binary runs against Ollama's Anthropic-compatible endpoint, so both lanes share hooks, MCP tools and the board protocol. That endpoint lacks prompt caching, `tool_choice` and token counting ([Ollama](https://docs.ollama.com/api/anthropic-compatibility)), which makes local sessions slower and less reliable, not unusable.

**One rule borrowed from Agent Deck.** Integrations never launch sessions; they post to the board and the reconciler dispatches. Otherwise a session launched elsewhere "becomes an orphan whose status events never route back" ([Agent Deck](https://github.com/asheshgoplani/agent-deck)).

**Mode.** Work/Life mode is a column on every row and a routing rule in code: Life text can only go to the Life DM.

Textual is still the most productive Python TUI. It is MIT-licensed, has the widgets a board needs, and kanban-tui shows drag-and-drop plus MCP working on it. But its main branch had 19 commits in June, 2 in July and none in August or September, and on October 9 its maintainer warned users to expect slow responses ([Textual on PyPI](https://pypi.org/pypi/textual/json), [Textual issue template](https://github.com/Textualize/textual/blob/main/.github/ISSUE_TEMPLATE/bug_report.md)). Pin the version and keep every rule behind the daemon API. If Textual stalls, you can swap the client for Ratatui, Bubble Tea v2, OpenTUI or a local web page without touching the core. It has no calendar widget, so budget a few hundred lines for a week grid built on its CSS grid layout.

### Two integration details decide the data model

**Linear.** An issue belongs to exactly one team, at most one project and at most one parent, but it can carry many attachments. An attachment is updated in place when the same issue and URL are reused, and attachments can be looked up by URL ([Linear schema](https://github.com/linear/linear/blob/master/packages/sdk/src/schema.graphql), [Linear attachments](https://linear.app/developers/attachments)). **That makes the attachment the only many-to-many link that doesn't clutter the team's shared projects or labels.** A Narwarp ticket groups issues through a local link table, which is the source of truth. Each link has a role: `tracks`, `spawned`, `mirror` or `mentions`. Each linked issue also gets one attachment pointing at the ticket's stable https URL, and the daemon reconciles periodically by URL lookup. Status rolls up by workflow-state *type*, not team-specific state names: Done only when every linked issue is completed, canceled or duplicate. Narwarp never pushes its own columns into Linear, because the mapping loses information. Without an admin you can't create webhooks ([Linear webhooks](https://linear.app/developers/webhooks)). But polling with a personal API key once a minute uses about 1.4% of the hourly query-cost budget, by Linear's published cost formula ([Linear rate limits](https://linear.app/developers/rate-limiting)).

**Google, email and GitHub.** Calendar writes need four habits: tag every block with private extended properties, give it a base32hex ID that Narwarp generates so retries can't create duplicates, update with `If-Match` etags, and treat a 412 conflict as your own edit, which pins the block ([extended properties](https://developers.google.com/workspace/calendar/api/guides/extended-properties), [events.insert](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert)). Focus Time exists only on Workspace primary calendars, so personal blocks are ordinary events that show as busy ([status events](https://developers.google.com/workspace/calendar/api/guides/calendar-status)). Publish your own Google OAuth client as "In production", even unverified, or refresh tokens expire every seven days ([Google OAuth](https://developers.google.com/identity/protocols/oauth2)). The `gmail.compose` scope can send as well as draft, so Narwarp's tool layer has to enforce draft-only ([Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)). GitHub's notifications API accepts only a classic personal access token, while agents should get repo-scoped fine-grained tokens that can't call the Checks API, so plan on two credentials ([GitHub notifications](https://docs.github.com/en/rest/activity/notifications), [GitHub tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)). Every source has a cursor (Linear `updatedAt`, Gmail `historyId`, Calendar sync tokens, GitHub `Last-Modified`), so a sleeping laptop loses nothing if the daemon catches up on wake.

### Where the notes disagree, and which side wins

**Storage is the biggest disagreement, and the standalone daemon wins.** The message-board notes put the boards in Narwarp's Diesel/SQLite because the fork already has 139 migrations of it. That choice assumed the harness lives in the fork. Their own requirements argue against that home. They call for a single-writer daemon, an MCP server, a CLI and hooks, and none of those needs the GUI. They already suggested a separate `boards.db` to keep database write contention away from UI state. And Diesel has no full-text-search API, so FTS5 would be raw SQL anyway. In the fork, agents can't post while Narwarp is closed. Every new table also edits `crates/persistence/src/schema.rs` and `app/src/persistence/sqlite.rs`, two files that Zap has also changed. The board schema still carries over table for table into the daemon's SQLite: principals, boards, messages, recipients, cursors, claims, handoffs, digests, approvals and FTS5. It merges with the ticket, run and external-link tables from the kanban notes.

## Zap went quiet while Warp started building your harness

### Freeze the fork and skip the merge

Zap is going quiet. Its last change taken from Warp landed on 2026-05-07. It made 10 commits in July, none in August, 4 in September and none so far in October, and its newest tag is still `v2026.07.09.1` ([Zap](https://github.com/zerx-lab/zap); local `git log upstream/main`). Warp is moving the other way. It had **596 commits from August 1 to October 13 by 57 authors**, and on October 9 it merged an "ACP client … and the ACP harness runner". Its new TUI has a multi-level orchestration UI, and its Agent CLI "works in any terminal emulator, including over SSH" ([Warp docs](https://docs.warp.dev/agents/cli/), [Warp](https://github.com/warpdotdev/warp)). Zap lacks 2,193 Warp commits and carries about 782 of its own, so moving Narwarp onto Warp isn't realistic either. Zap's own roadmap points your way. It plans "a standalone open-source agent service … not tied to Warp's existing client code" ([Zap roadmap](https://github.com/zerx-lab/zap/blob/main/docs/roadmap.md)), and nothing shows that work has started.

Two parts of the question rest on mistaken premises. **"Unwarp" is not an upstream**: it is this fork's original name (`62ae71c7`, renamed to Narwarp in `55ffe36f` on 2026-06-05), so "pull the latest" can only mean merging Zap into your work. And **your work is not on `main`**: `main` is still Zap's `bbcdbc12`, and only `phase-4/watcher-and-polish` carries the 33 Narwarp commits (local `git merge-base --is-ancestor`). **A trial merge of Zap's 60 new commits conflicts in 4 files and 9 hunks.** 328 of the roughly 467 conflicting lines are in the 22,334-line `workspace/view.rs`. The last sync needed a separate commit to fix 88 compile errors (`6e14311e`). What you'd gain is mostly Windows, translation, SSH and image-viewer fixes. Microsoft's study of the Edge fork found build breaks to be the costly kind of conflict between a fork and its upstream ([Microsoft Research](https://microsoft.com/en-us/research/?p=640647)). Every new Narwarp view would widen that conflict area, because each one has to be wired through `view.rs`, `left_panel.rs`, settings and `schema.rs`.

So fast-forward your fork's `main` to `b9b9e760`, the `phase-4` tip, which builds directly on `main`, and tag it. Keep Narwarp as your daily terminal; Zap's CLI-agent blocks already show Claude Code sessions. Start the harness in a new Python repo. That is neither "start from scratch" nor "update and build from there": the designs move, and the WarpUI code stays behind. The sunk cost is small. **31 of the 33 commits were co-written with Claude, and most of the layer landed in three days in May** (local `git log`).

Revisit this only if Zap ships its agent service or Warp's ACP runner makes official Warp a better host. Even then, integrate over ACP or MCP rather than forking again.

On licensing, purely personal use of an AGPL program creates no duty to publish its source ([GNU FAQ](https://www.gnu.org/licenses/gpl-faq.en.html)). A new repo holding only your own code can be MIT or private. Your redactor and chunker were written as standalone modules (`31d5df89`), so they are yours to port. Copying code from Toad, which is AGPL, would bring AGPL terms into the new repo ([Toad](https://github.com/batrachianai/toad)).

Paperclip has a real case. It already covers much of your list, its many-to-many external-object tables are the best existing model for grouping Linear issues, and two separate "companies" in one deployment would give Work and Life a hard boundary. It still loses on four counts. It lacks the features that define your product: calendar carving, Work/Life output routing, ritual-based accountability and Linear grouping under personal tickets are things no ticket-centric tool has. Its stack is TypeScript on Postgres with 167 table modules. An upstream that tags releases almost daily will break your extensions every week. And it is built for someone with "20 simultaneous Claude Code terminals open" ([Paperclip README](https://github.com/paperclipai/paperclip/blob/master/README.md)), while your limit is one person's review time. The wider field points the same way. Vibe Kanban is sunsetting, Automaker says it "is no longer actively maintained" ([Automaker](https://github.com/AutoMaker-Org/automaker/blob/main/LICENSE)), and Kanbots, ticket and dex have stalled. **Copy schemas and behaviors; don't take a runtime dependency.**

Beyond Paperclip and Multica, four more things are worth copying. From Beads, take its single-step claim of a task and its Linear sync rules, in which the newer timestamp wins conflicts by default, switches can favor either side, and a five-minute debounce stops agents triggering sync loops ([Beads Linear sync](https://github.com/gastownhall/beads/blob/main/docs/cli-reference/linear.md)); add your own rule that every synced field has exactly one owner. From MCP Agent Mail, take the split between message rows and per-recipient read and acknowledged rows ([Agent Mail](https://github.com/Dicklesworthstone/mcp_agent_mail)). From Symphony, take the idea that a run succeeds when it reaches "Human Review", not Done. From Linear, take the agent-activity vocabulary of thought, action, elicitation (a question to the human), response and error ([Linear](https://linear.app/developers/agent-interaction)).

The first slice deliberately leaves out Linear, the calendar, Discord, email, digests and retrieval, because none of them tests the riskiest assumption: that a board-driven loop around Claude Code beats opening sessions by hand. It contains the ticket, run and ticket-event tables plus the board tables (messages, recipients, claims, handoffs, approvals), with `narwarpd` as their only writer behind a local API. The CLI offers `nw add`, `nw board`, `nw start`, `nw post` and `nw approve`, and triage runs rules plus a local model with the Inbox as fallback. Each ticket is dispatched to a background session in its own worktree, where `SessionStart` injects the ticket context, `UserPromptSubmit` injects message headers, and an HTTP hook sink receives stop, notification and permission events. Agents get six MCP tools (`start_session`, `post`, `ask`, `claim`, `handoff_write` and `request_approval`), and you get a Textual board with five columns, one row per project, a Work/Life toggle, a "Needs you" queue and a single key to attach to a session. At your May pace, when about 9,500 lines went into the fork in three days, this is a short build. **The exit test matters more than the feature count.** If you still open Claude sessions by hand after a week, fix the loop before adding integrations.

## Conclusion

What you described is less a terminal than an attention router for one person across work and life, and the terminal is its least distinctive part. That is the strongest reason to stop investing in the fork: what makes the fork unique, being a terminal, is what the harness needs least. Six of the twelve systems are plain code and three more are tightly constrained local-model jobs, so model capability is not the main risk. The real risks are permissions you don't control and whether you are still using it in month six. You need a Linear admin for webhooks, a Discord admin for a bot and a Workspace admin for calendar access. So fallback modes, and a first slice that is useful with no integrations at all, are worth more than any single feature on the list.

Plan for change rather than stability. Claude Code shipped about 300 releases between January and October 2026, and agent view and channels are still previews. Anthropic's own harness team writes that "every component in a harness encodes an assumption about what the model can't do on its own" ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)). Pin versions, keep the Claude adapter to a few hundred lines, and re-check the watchdog, digests and gates at each model upgrade. The parts most likely to become dead weight are the ones that compensate for weak models. The parts most likely to last are the store, the gates and the rituals.
